### [1] FetchModels 裸 client 跟随 redirect 无复查

| Field | Value |
| --- | --- |
| Severity | medium |
| Confidence | high |
| Category | ssrf |
| CWE | CWE-918 |
| Affected lines | controller/channel.go:1305, controller/channel.go:1227-1230 |

#### Summary

`FetchModels`（`controller/channel.go:1232`）在非 Gemini/Ollama 分支使用裸
`client := &http.Client{}`（`channel.go:1305`），该 client 无 `CheckRedirect` 回调。
`validateFetchModelsURL`（`channel.go:1227-1230`）只校验初始 URL，跳转后不复查目标，
可被用于探测内网 80/443/3000/8080/8443 等端口。此外 Anthropic 分支的 `x-api-key` 头
不在 Go 跨域跳转自动剥离名单内，会随 redirect 外带到任意目标。

#### Root Cause

`FetchModels` 的非 Gemini/Ollama 分支直接构造 `&http.Client{}`，未复用
`service.GetHttpClient()`（该 client 已配置 `CheckRedirect: checkRedirect`，会对每次
跳转复查 SSRF 规则）。

#### Validation

确认 `controller/channel.go:1305` 仍为 `client := &http.Client{}`，无 `CheckRedirect`。
对比 `service/http_client.go:171-179`，`newRelayHTTPClient` 创建的 client 带
`CheckRedirect: checkRedirect`，`GetHttpClient()` 返回该实例。`validateFetchModelsURL`
（`channel.go:1227-1230`）调用 `common.ValidateURLWithFetchSetting`，仅校验初始 URL。

#### Dataflow

Root 用户 POST `/api/channel/fetch_models` → `FetchModels` → `validateFetchModelsURL(url)`
校验初始 URL → `client := &http.Client{}` → `client.Do(request)` → 上游返回 301/302/307/308
→ 裸 client 自动跟随跳转，不复查目标 URL → 内网端口探测 / `x-api-key` 头外带。

#### Reachability

需 Root 权限（`router/api_router.go:188` 中 `FetchModels` 挂在 `middleware.RootAuth()` 下，
复核基线 commit `7769ff7d4` 同样如此）。攻击者需 root 权限，极大限制了攻击者群体，
但可探测内网服务并可能泄露 Anthropic API key。

#### Severity

**Medium** — 需要 root 权限，但可导致内网端口探测和 API key 经 redirect 外带。
`report.md` 的 Assumptions 中将渠道 base URL 视为"admin-configured trusted inputs"，
但 `FetchModels` 接受请求体中的 `base_url` 字段，root 可传入任意值。

#### Remediation

将 `controller/channel.go:1305` 的 `client := &http.Client{}` 替换为
`service.GetHttpClient()`，复用带 `checkRedirect` 的受控 client。

### [2] 支付回调过早确认

| Field | Value |
| --- | --- |
| Severity | medium |
| Confidence | high |
| Category | business_logic |
| CWE | CWE-841 |
| Affected lines | controller/topup.go:262-283, controller/topup_stripe.go:182, controller/topup_stripe.go:244-248 |

#### Summary

**Epay**：`controller/topup.go:262-266` 在签名验证通过后立即向支付平台写回 `success`，
之后才执行 `model.CompleteEpayTopUp`（`topup.go:280`）。若入账失败（数据库错误等），
平台已收到 `success` 不会重试，导致"已扣款未到账"。

**Stripe**：`controller/topup_stripe.go:182` 无条件返回 `c.Status(http.StatusOK)`。
`fulfillOrder`（`topup_stripe.go:244-248`）中 `model.Recharge` 失败仅 `log.Println` 后
`return`，但外层仍返回 200，Stripe 不会重投。

#### Root Cause

Epay 回调在入账前就确认；Stripe webhook 对入账失败分支未返回 5xx 触发平台重投。

#### Validation

确认 `controller/topup.go:262-266`：

```go
if err == nil && verifyInfo.VerifyStatus {
    _, err := c.Writer.Write([]byte("success"))
    // ...
} else {
    // ...
    return
}
```

`success` 在签名验证通过后立即写入，`CompleteEpayTopUp`（`topup.go:280`）在之后执行。

确认 `controller/topup_stripe.go:182`：`c.Status(http.StatusOK)` 在 switch 之后无条件
执行。`fulfillOrder`（`topup_stripe.go:244-248`）中 `Recharge` 失败仅记日志。

#### Dataflow

**Epay**：支付平台 POST `/api/user/epay/notify` → 签名验证通过 → `c.Writer.Write("success")`
→ `CompleteEpayTopUp` → 若失败，平台不重试。

**Stripe**：Stripe POST `/api/stripe/webhook` → `webhook.ConstructEvent` 验签 →
`fulfillOrder` → `model.Recharge` 失败 → `log.Println` → `return` → `c.Status(200)`。

#### Reachability

Epay 回调端点匿名可达（`router/api_router.go` 中 Epay notify 无 Auth middleware）。
Stripe webhook 端点匿名可达。攻击者无需认证，但需构造有效签名（Epay）或等待真实
支付事件触发。瞬时数据库错误即可导致资金状态不一致。

#### Severity

**Medium** — 可导致"已扣款未到账"的资金状态不一致，影响计费账本完整性。需要特定
触发条件（支付完成 + 入账失败），但后果严重且不可自动恢复。

#### Remediation

- Epay：将 `c.Writer.Write("success")` 移到 `CompleteEpayTopUp` 成功之后。
- Stripe：`fulfillOrder` 中 `Recharge` 失败时返回 5xx（需将错误传递到外层 handler），
  触发 Stripe 重投。

### [3] 2FA 登录 pending session 无时效

| Field | Value |
| --- | --- |
| Severity | low |
| Confidence | high |
| Category | authentication_failures |
| CWE | CWE-613 |
| Affected lines | controller/user.go:87-88, controller/twofa.go:351-362, main.go:148, controller/secure_verification.go:29 |

#### Summary

登录（`controller/user.go:84-93`）设置 `pending_username` / `pending_user_id` 时未存储
时间戳。`Verify2FALogin`（`controller/twofa.go:344-362`）仅检查 `pending_user_id` 是否
存在，不校验时效。session cookie MaxAge 为 2592000（30 天），攻击者知道密码后可在
长达 30 天窗口内反复尝试 TOTP/备用码。安全验证（step-up）流程已有
`SecureVerificationTimeout=300`（`controller/secure_verification.go:29`），此处漏配。

#### Root Cause

2FA 登录 pending session 实现时未存储时间戳或强制有效期，与 SecureVerification
step-up 流程不一致。

#### Validation

确认 `controller/user.go:87-88`：

```go
session.Set("pending_username", user.Username)
session.Set("pending_user_id", user.Id)
```

无时间戳。确认 `controller/twofa.go:351-362`：仅检查 `pending_user_id` 是否 nil 及类型
断言，无过期检查。`main.go:148` 设置 `MaxAge: 2592000`。
`controller/secure_verification.go:29` 定义 `SecureVerificationTimeout = 300`。

#### Dataflow

POST `/api/user/login` → `user.ValidateAndFill` 成功 → `session.Set("pending_user_id", user.Id)`
（无时间戳）→ POST `/api/user/login/2fa` → `Verify2FALogin` 读取 `pending_user_id` →
仅检查存在性 → 验证 TOTP/备用码 → `setupLogin`。

#### Reachability

未认证攻击者知道用户密码即可发起登录，获得 2FA 挑战后可在 30 天内反复提交。2FA 锁定
（5 次/300s）在每次锁定结束后重置，允许恢复猜测。

#### Severity

**Low** — 扩大了暴力破解窗口，但 2FA 锁定和限速提供部分缓解；攻击者需已知密码。
与 `report.md` finding-2 一致。

#### Remediation

设置 pending session 时同时存储时间戳（如 `session.Set("pending_user_id_set_at", now)`）。
`Verify2FALogin` 中校验 `now - pending_user_id_set_at >= 300` 则拒绝（复用
`SecureVerificationTimeout`）。超时后清除 pending 字段。

### [4] CRYPTO_SECRET 静默回落 SessionSecret

| Field | Value |
| --- | --- |
| Severity | low |
| Confidence | high |
| Category | configuration |
| CWE | CWE-1188 |
| Affected lines | common/init.go:62-66 |

#### Summary

未配置 `CRYPTO_SECRET` 环境变量时，`common/init.go:62-66` 静默回落到 `SessionSecret`。
多实例部署下 `/mcp/image|video` 签名 URL 重启后全失效、实例间互拒。`SESSION_SECRET`
有默认值检测告警，但 `CRYPTO_SECRET` 回落时无任何启动告警。

#### Root Cause

`CRYPTO_SECRET` 回落逻辑未像 `SESSION_SECRET` 那样输出显式告警。

#### Validation

确认 `common/init.go:62-66`：

```go
if os.Getenv("CRYPTO_SECRET") != "" {
    CryptoSecret = os.Getenv("CRYPTO_SECRET")
} else {
    CryptoSecret = SessionSecret
}
```

无任何 `log.Println` 或告警。对比 `common/init.go:52-61`，`SESSION_SECRET` 设为
`random_string` 时有 `log.Fatal`。

#### Dataflow

启动 → `os.Getenv("CRYPTO_SECRET")` 为空 → `CryptoSecret = SessionSecret` → 无告警 →
多实例间签名 URL 互拒。

#### Reachability

多实例部署且未配置 `CRYPTO_SECRET` 时触发。单实例部署无直接影响，但重启后签名 URL
失效（若 `SESSION_SECRET` 也未配置则每次重启随机生成）。

#### Severity

**Low** — 影响多实例部署的可用性，不直接导致安全问题，但可能导致签名 URL 失效后
用户无法访问已上传媒体。

#### Remediation

回落时打印显式启动告警（如 `log.Println("WARNING: CRYPTO_SECRET not set, falling back to SessionSecret...")`）。
多实例部署文档要求独立配置 `CRYPTO_SECRET`。

### [5] 版本指纹全响应暴露

| Field | Value |
| --- | --- |
| Severity | low |
| Confidence | high |
| Category | information_disclosure |
| CWE | CWE-200 |
| Affected lines | middleware/cors.go:20, controller/misc.go:99 |

#### Summary

`middleware/cors.go:20` 通过 `PoweredBy()` 中间件对所有响应设置
`X-New-Api-Version: <commit>` 响应头。`controller/misc.go:99` 在 `/api/status` 响应体中
返回 `"version": common.Version`。匿名即可获取精确 commit 指纹，用于匹配该版本公开漏洞。

#### Root Cause

版本信息在全局响应头和公开状态接口中无条件暴露，未按角色限制。

#### Validation

确认 `middleware/cors.go:18-22`：

```go
func PoweredBy() gin.HandlerFunc {
    return func(c *gin.Context) {
        c.Header("X-New-Api-Version", common.Version)
        c.Next()
    }
}
```

`main.go:142` 注册 `server.Use(middleware.PoweredBy())`，对所有请求生效。

确认 `controller/misc.go:99`：`"version": common.Version` 在 `/api/status` 响应体中，
该接口匿名可达（`router/api_router.go:23`）。

#### Dataflow

任意请求 → `PoweredBy()` 中间件设置 `X-New-Api-Version` 响应头 → 匿名获取 commit 指纹。
GET `/api/status` → 响应体含 `version` 字段 → 匿名获取 commit 指纹。

#### Reachability

任何匿名网络访问者即可获取。

#### Severity

**Low** — 仅泄露版本指纹，不直接导致入侵，但可辅助攻击者匹配已知漏洞。`controller/AGENTS.md`
的"受众隔离"原则要求公开接口不返回角色受限数据，版本指纹属于管理语义不应进公开面。

#### Remediation

两处一并收敛：`PoweredBy()` 中间件改为仅登录/管理员可见（或移除），`/api/status` 的
`version` 字段移到 `AdminAuth` 保护的独立接口。

### [6] 未初始化实例的 setup 抢注窗口

| Field | Value |
| --- | --- |
| Severity | low |
| Confidence | high |
| Category | access_control |
| CWE | CWE-862 |
| Affected lines | router/api_router.go:21-22 |

#### Summary

`/api/setup`（GET + POST）匿名可达（`router/api_router.go:21-22`）。新部署首次暴露公网
时存在 root 账户抢注窗口：代码内有并发锁，但防不住首次外部抢注。

#### Root Cause

首次初始化接口设计为匿名可达，未绑定监听地址限制或初始化令牌。

#### Validation

```go
apiRouter.GET("/setup", controller.GetSetup)
apiRouter.POST("/setup", anonymousRequestBodyLimit, controller.PostSetup)
```

无 `AdminAuth()` 或 `UserAuth()`。`controller.PostSetup` 内有并发锁但仅防重复初始化。

#### Dataflow

新部署实例暴露公网 → 攻击者 POST `/api/setup` → 若先于合法管理员到达 → 抢注 root 账户。

#### Reachability

仅未初始化实例（`constant.Setup == false`）暴露公网时可触发。已初始化实例不受影响。

#### Severity

**Low** — 需要实例未初始化且暴露公网，属部署侧责任。`report.md` Assumptions 中明确

#### Remediation

### [7] 低优先级代码质量项

| Field | Value |
| --- | --- |
| Severity | low |
| Confidence | high |
| Category | code_quality |
| CWE | CWE-20 |
| Affected lines | service/custom_voice.go:602, service/custom_voice.go:636, model/channel.go:363-406, controller/uptime_kuma.go:131 |

#### Summary

三个子项：

1. **GroupId 拼接未编码**（`service/custom_voice.go:602, 636`）：`url += "?GroupId=" + up.groupId`
   未对 `groupId` 做 URL 编码，含 `&`/`#` 时污染上游请求参数。`groupId` 来自渠道 `Other`
   字段（管理员填写），非用户直接可控，但违反输入校验原则。

2. **SearchChannels 无 LIMIT 全量加载**（`model/channel.go:363-406`）：`SearchChannels`
   无分页 LIMIT，全量加载到内存后由调用方分页。渠道量大时放大内存/CPU 消耗。

3. **uptime_kuma 匿名内网请求**（`controller/uptime_kuma.go:131`）：`/api/uptime/status`
   匿名可触发服务端内网请求（≤40 个/次），可被用于内网探测。

#### Root Cause

输入未编码、查询未分页、匿名接口未限制出站请求。

#### Validation

确认 `service/custom_voice.go:602` 和 `636`：

```go
url += "?GroupId=" + up.groupId
```

未使用 `url.Values`。确认 `model/channel.go:402`：`baseQuery.Order(order).Find(&channels)`
无 `Limit`。确认 `controller/uptime_kuma.go:131`：`GetUptimeKumaStatus` 无 Auth middleware
（`router/api_router.go:29`：`apiRouter.GET("/uptime/status", controller.GetUptimeKumaStatus)`）。

#### Severity

**Low** — GroupId 为管理员填写非用户可控；SearchChannels 需 admin 触发；uptime_kuma
内网请求受配置的 URL 限制。三者风险有限但应修复。

#### Remediation

- `service/custom_voice.go:602, 636`：改用 `url.Values` 编码 GroupId。
- `model/channel.go:363-406`：改 SQL 层分页，加 `Limit` / `Offset`。
- `controller/uptime_kuma.go:131`：考虑加登录态或结果缓存。

### report.md finding-1（AdminResetPasskey）复核

`report.md` 报告 `AdminResetPasskey`（`controller/passkey.go:475-509`）缺少角色层级检查，
允许非 root admin 删除 root 用户的 passkey。中文清单未收录此项。

复核确认：`controller/passkey.go:475-509` 中 `AdminResetPasskey` 加载目标用户后直接调用
`model.DeletePasskeyByUserID(user.Id)`，无 `myRole <= targetUser.Role` 检查。对比
`AdminDisable2FA`（`controller/twofa.go:451`）和 `ManageUser`（`controller/user.go:762`），
两者均执行 `myRole <= targetUser.Role && myRole != common.RoleRootUser` 检查。

此项在中文清单中遗漏，本报告补充定级为 **medium**，与 `report.md` 一致。

| Field | Value |
| --- | --- |
| Severity | medium |
| Confidence | high |
| Category | access_control |
| CWE | CWE-862 |
| Affected lines | controller/passkey.go:475-509, router/api_router.go:119 |

#### Remediation

在 `AdminResetPasskey`（`controller/passkey.go:475-509`）中添加角色层级检查，匹配
`AdminDisable2FA`（`controller/twofa.go:451`）和 `ManageUser`（`controller/user.go:762`）
的模式：`myRole <= targetUser.Role && myRole != common.RoleRootUser` 时拒绝。
