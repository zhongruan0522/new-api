### `dfc0d6324` 用户设置更新竞态可回滚已消费配额（安全通告合并修复，fork 残余三个子项）

上游修复内容：①`PUT /api/user/self` 任意 JSON 反序列化为 `model.User` 全量 Updates（mass assignment 可改 quota）；②设置更新走全行 Update，读-改-写竞态内用过期快照覆盖 `quota`/`used_quota`/`request_count`；③`updateUserCache` 把快照 Quota 写回缓存；④`PUT /self` 缺 `CriticalRateLimit`。

涉及文件：
1. `model/user.go` → `internal/model/user.go`（`Update` 无 `Omit("quota","used_quota","request_count")`）
2. `model/user_cache.go` → `internal/model/user_cache.go:66-75`（`updateUserCache` 经 RedisHSetObj 全量写含 Quota 的 UserBase）
3. `controller/user.go` → `internal/controller/user.go`（`UpdateUserSetting` 取全量快照后调 `user.Update(false)`）
4. `router/api-router.go` → `internal/router/api_router.go:76`（`PUT /user/self` 无 CriticalRateLimit）

原因（fork 现状证据）：
1. 子项①fork 已免疫：`UpdateSelf` 用 `cleanUser` 白名单（`internal/controller/user.go:596-601` 仅 Id/Username/Password/DisplayName）。
2. 子项②③仍成立：`internal/controller/user.go` 的 `UpdateUserSetting` 先 `GetUserById` 取全量快照，改 setting 后调 `user.Update(false)`；`internal/model/user.go:421-437` 的 `Update` 用 `DB.Model(user).Updates(newUser)` 把快照全部非零字段回写且不 Omit 计费三字段——并发消费期间反复 `PUT /user/setting`，快照中非零的旧 Quota 会覆盖当前值，**用户可借此恢复已耗额度**（免费刷配额）。
3. 子项④仍成立：`PUT /user/self`（`internal/router/api_router.go:76`）与 `PUT /user/setting`（`:96`）均未挂 `CriticalRateLimit`（同组 `register`/`reset_password`/`topup` 均有挂），竞态可高频执行。

应当表现为：
1. 新增只更新 setting 列的 `UpdateUserSetting(userId, setting)`；`Update`/`Edit` 路径 `Omit("quota","used_quota","request_count")`；`updateUserCache` 不写 Quota（配额统一由原子增量路径维护）；`PUT /user/self` 挂 `CriticalRateLimit`；参照上游补 user_update 回归测试（先证伪再修复）。

### 富文本渲染安全六连 `f4473d963` + `0b48ad86d` + `626dadb55` + `fda817786` + `1f4d8d2b2` + `17465b855`（fork 语境升级为 P0）

2. `web/src/features/legal/legal-document.tsx:145` —— 同上
3. `web/src/components/layout/components/footer.tsx:232` —— 同上（页脚 HTML）
4. `web/src/components/ui/markdown.tsx` —— react-markdown + remark-gfm + `rehypeRaw` **且无 sanitize**（首页自定义内容/公告经此渲染）
5. `web/src/features/home/index.tsx:48` —— 自定义首页 iframe 无 `sandbox` 属性
6. `web/package.json:94` —— `dompurify` 仅作为 overrides 钉在 3.4.5，`web/src` 内零调用（死依赖）

原因：
1. 管理员配置的关于页/法律文档/页脚/首页内容被原样注入 DOM，`<img onerror>`、内联事件等存储型 XSS 直接可打；内容源虽是管理员，但账号失窃或配置写入漏洞即升级为全站访客执行脚本。

2. 实施时需按 fork 的 i18n 嵌套 key 体系与 `@/components/ui/dialog` 路径适配，不可直接 cherry-pick。

### `0cd9dc85e` 用户资料全量回写竞态（access_token 轮换/邀请奖励原子化，安全修复合并）

涉及文件：
1. `internal/controller/user.go`（`GenerateAccessToken` :337-364）
2. `internal/model/user.go`（`User.Update` / `inviteUser`）

原因：
1. fork 的 `GenerateAccessToken` 加载整个 user 后调用 `user.Update(false)`，而 `User.Update` 用 struct 非零字段全量 `Updates` 回写，快照里的 Quota/UsedQuota/AffQuota 会覆盖并发中继扣费的结果（丢失更新窗口）。
2. `inviteUser` 同样是 load-modify-`DB.Save(user)` 全行回写。fork 无 `UpdateUserAccessToken` 定向更新函数。

应当表现为：
1. `GenerateAccessToken` 只做 `UPDATE users SET access_token=? WHERE id=?`（校验 RowsAffected）；`inviteUser` 用 `gorm.Expr` 原子自增 aff_count/aff_quota/aff_history；`UpdateSelf` 路径 Omit `access_token`、`aff_*` 等并发字段。

> **合并注**: 与 rc.14~rc.20 批次 `dfc0d6324`（本篇首条）同根源——`User.Update` 的 struct 非零
> 字段全量回写被多个调用点复用，修复时应统一收口（定向更新列 / Omit 并发敏感字段），
> 而非逐调用点打补丁。[修复](修复.md) 篇「计费 / 协议正确性」的 `d7992672a`（OAuth 绑定
> 全量快照写回）属同一家族。

### `47ba9d2c6` 充值入账守护钱包额度上限（int32 天花板防溢出）

涉及文件：
1. `internal/model/topup.go`（入账路径 :242/:473）
2. `internal/controller/topup.go`

原因：
1. fork 的 `users.quota` 列为 `type:int`（`internal/model/user.go:33`，MySQL 下 int32 上限约 21.47 亿；QuotaPerUnit=500000 时约 $4300 即溢出）。

涉及文件：

### `0bf42781d` + `35074345e` + `f250f3b58` dompurify 口径统一：传递链 CVE 风险实存，升级或清理须同批处置（合并批）

> 本条为拆分时合并的「结论相反、应同批落地」批次：原 [修复](修复.md) 篇「渠道 / 前端修复」
> 末条 `f250f3b58`（判定"残留依赖零风险"）与本节原 `0bf42781d` + `35074345e`（判定"传递链
> CVE 风险实存"）结论相反，已复核后并为一条。

涉及文件：
1. `web/package.json`（:94，overrides 中 `"dompurify": "3.4.5"`）
2. `web/bun.lock`

原因（两批结论相反，已复核统一）：
1. rc.14~rc.20 批次（`0bf42781d` + `35074345e`）判定：fork 的 dompurify 是真实运行时依赖链一环（`streamdown` → `mermaid` → dompurify），被 overrides 强制钉在 3.4.5；3.4.5 受 CVE-2026-49458 / CVE-2026-49459（XSS bypass，3.4.6 修复）、CVE-2026-49978（3.4.7 修复）影响。
2. rc.21~rc.25 批次（`f250f3b58`）判定："全库无 dompurify import，属残留依赖不进 bundle，实际风险面为零——依赖卫生项"，仅建议"同步 3.4.13 或走 knip 清理残留依赖"。**与上条结论相反。**
3. 2026-08-20 复核裁定：`web/bun.lock` 中 `streamdown`（直接依赖，`web/src/components/ai-elements/response.tsx` 在用）→ `mermaid` → `dompurify` 传递链确实存在（`web/src` 内确无直接 import，"零风险"判定系未检出该传递链），CVE 升级结论依然成立。若落地本篇 P0「富文本渲染安全六连」的消毒方案，dompurify 将从传递依赖变为直接使用，升级更加必要。

应当表现为：
1. overrides 钉值升至 ≥3.4.11（与上游 `0bf42781d` 对齐，有条件时同步 `f250f3b58` 的 3.4.13）并同步 bun.lock；若经评估确认放弃升级，则走 knip 清理残留依赖——两条路径二选一，但必须同批一次处置，不允许"升级"与"零风险保留"两个口径并存。`bun install`、`bun run build`、`bun run typecheck` 通过，mermaid 图表渲染回归正常。
